== 1. 🔴 (1) LỖI SAU KHI GHI BỊ ĐÁNH FAILED ⇒ ĐẨY NGƯỜI DÙNG SANG COMMAND_ID MỚI ==
Cơ chế: `/execute` bắt mọi exception của `executePaymentProposal()` rồi
`store.fail(command_id, …)` ⇒ 500. Nhưng lỗi có thể xảy ra SAU khi
`store.setReference(commandId, commandId)` (đã đăng ký reference) — tức là
ERPNext CÓ THỂ đã ghi document và chỉ mất response. Hệ quả kép:
  · `begin()` TỪ CHỐI command FAILED ⇒ lần retry cùng id bị 409 terminal ⇒
    KHÔNG BAO GIỜ đi vào nhánh reconcile ⇒ không cách nào phát hiện document
    đã tồn tại;
  · người dùng bị đẩy sang "tạo command_id mới" (đúng thứ Flutter từng làm,
    đã sửa ở result24) ⇒ GHI PHIẾU THỨ HAI.
Fix (phân loại theo reference, fail-closed):
  const afterWrite =
    err?.code === "PAYMENT_WRITE_UNVERIFIED" || Boolean(store.status(command_id)?.reference_no);
  if (afterWrite) → 503 { ok:false, retry_same_command_id:true, error:"… gửi lại
    ĐÚNG command_id này để hệ thống đối soát với ERPNext (KHÔNG tạo command_id mới)" }
    và KHÔNG gọi store.fail ⇒ record giữ PENDING (lần sau reconcile được).
  ngược lại (lỗi TRƯỚC setReference: chưa thể ghi gì) → FAILED + 500 như cũ.
Bất biến được dùng để phân loại: reference_no CHỈ được set ngay trước lệnh write,
nên "có reference" ⟺ "đã có thể đã ghi".
Test hồi quy: "/execute: a transient write failure keeps the command PENDING
  (503, retry the SAME id) and never burns it as FAILED" — dùng fault injection
  mới trong mock: MOCK_ERP_FAIL_WRITE=1 ⇒ erpnext_doc_create ném lỗi.

== 2. 🔴 (2) `amount_vnd: 0` / NaN BỊ THĂNG CẤP THÀNH "THU TOÀN BỘ NỢ" ==
Cơ chế: executor tính
    const paid = Math.min(Math.round(Number(proposal.params?.amount_vnd) || liveOutstanding), liveOutstanding);
`Number(x) || liveOutstanding`: 0, NaN, "" đều là falsy ⇒ rơi về liveOutstanding
⇒ một proposal gửi amount 0 được THĂNG CẤP thành thu HẾT NỢ. Trớ trêu: chính
`buildPaymentProposal()` ĐÃ từ chối `amount <= 0` (PAYMENT_AMOUNT_INVALID) ⇒
**cùng một field được validate ở đường build nhưng KHÔNG ở đường execute**, mà
`/execute` nhận proposal TỪ CLIENT (không bắt buộc do builder sinh ra).
Fix 2 tầng (defense in depth):
  · Boundary `/execute` (trước store.begin, KHÔNG chiếm command_id):
      const amountVnd = Number(proposal.params?.amount_vnd);
      if (!Number.isFinite(amountVnd) || amountVnd <= 0) → 400
        { error: "params.amount_vnd phải là số VND > 0" }
  · Executor (trước setReference ⇒ chưa đăng ký, chưa ghi):
      throw { code:"PAYMENT_AMOUNT_INVALID" } khi không phải số hữu hạn > 0.
Test hồi quy:
  "/execute: an invalid amount is refused at the boundary and does NOT burn the
   command_id"  → amount 0 · -1 · "abc" · null đều 400; store.status(cid) === null;
   sau đó gửi lại ĐÚNG id với amount hợp lệ ⇒ 200, paid_vnd = 2.500.000
   (không phải toàn bộ nợ).
  "Stage B: an invalid amount is refused and NEVER promoted to the full debt"
   → 0 · -5 · null · "không rõ" đều throw PAYMENT_AMOUNT_INVALID; 0 write;
   reference_no không được đăng ký.

== 3. 🟡 (3) `?? modes[0]?.name` CHỌN ĐẠI PHƯƠNG THỨC THANH TOÁN ==

== 4. 🟡 (4) `Number(x) <= 0` ĐỂ LỌT NaN (payload `paid_amount: null`) ==
Cơ chế: kiểm tra khoản phải thu là `Number(target.outstanding_amount) <= 0`,
nhưng `NaN <= 0` là false ⇒ dòng outstanding "rác" (vd "abc") lọt qua, tiếp đó
`Math.round(NaN)` = NaN ⇒ JSON.stringify(NaN) = null ⇒ payload paid_amount null.
Fix: `Number.isFinite(rawOutstanding) && rawOutstanding > 0` (giữ nguyên
  `rawOutstanding <= 0` ⇒ bắt cả trường hợp bình thường).
Test hồi quy: "Stage B: a non-numeric outstanding amount is refused (NaN must not
  reach the payload)" → "abc" ⇒ PAYMENT_INVOICE_NOT_RECEIVABLE;
  "" ⇒ PAYMENT_INVOICE_ALREADY_SETTLED (bị lọc từ trước, cũng 0 write).
