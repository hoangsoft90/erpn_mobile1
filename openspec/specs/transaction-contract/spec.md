# transaction-contract Specification

## Purpose
Khả năng `transaction-contract`: hợp đồng nền cho mọi màn giao dịch — handoff do server cấp và thuộc về principal của nó; prefill chỉ mang trạng thái và id, KHÔNG bao giờ mang số tiền; Transaction Draft là đầu vào DUY NHẤT để dựng proposal; route propose KHÔNG ghi; hoá đơn mở không bao giờ được tự chọn; một phương thức cho mỗi lần thu; `payment.create` là canonical và `payment.collect` là alias cùng policy.

## Requirements

### Requirement: A business handoff is issued by the server and owned by its principal

When a routed WRITE-intent sentence cannot be answered with a proposal, the
answer MUST carry a `business_handoff` whose `handoff_id` was generated by the
server. No value supplied by a client may ever be accepted as a ticket id, and
no code path may mint a ticket from outside the handoff builder. A ticket MUST
be readable only by the principal it was issued to; a request carrying another
principal's ticket, another conversation's ticket, an unknown id, or an expired
id MUST be refused in exactly the same way, so a caller cannot probe which ids
are alive. A ticket that could not be stored MUST NOT be handed to the client.

#### Scenario: the ticket is server-generated and names the capability and screen

- **WHEN** a collect sentence is routed and cannot be answered with a proposal
- **THEN** the answer carries a `business_handoff` with a server-generated
  `handoff_id`, the canonical capability id, and the screen it opens

#### Scenario: a fabricated id is refused like an expired one

- **WHEN** a request presents an id that was never issued
- **THEN** it is refused with the stale-ticket code and no proposal — the same
  refusal an expired ticket produces

#### Scenario: ownership is principal AND conversation bound

- **WHEN** a ticket issued to principal A is presented by principal B, or in a
  different conversation of the same principal
- **THEN** the request is refused with the same stale-ticket code and no
  proposal, and the refusal does not reveal whether the id exists

#### Scenario: a ticket that failed to store is never handed out

- **WHEN** storing a ticket is refused (for example no owner principal)
- **THEN** no handoff is attached to the answer, and the refusal is returned
  rather than thrown

### Requirement: A handoff prefill carries states and ids, never an amount

A ticket's prefill MUST describe **what the sentence already settled** and
**what the form still needs**, using only the state vocabulary
`RESOLVED | AMBIGUOUS | MISSING | NO_MATCH`, plus ids, labels and picker
candidates. A ticket MUST NOT carry an amount, an outstanding balance, or any
other number that a client could later present as server-supplied authority;
building a ticket that carries one MUST fail. The ticket TTL bounds memory of an
abandoned conversation only — it is NOT a freshness guarantee for document data.

#### Scenario: no authoritative number can enter a ticket

- **WHEN** a handoff is built with a prefill slot carrying an amount or an
  outstanding balance
- **THEN** the build fails instead of issuing a ticket

#### Scenario: slot states say what is missing

- **WHEN** a collect sentence settles the customer but carries no amount
- **THEN** the customer slot reads `RESOLVED` and the missing slots read
  `MISSING`; an ambiguous customer reads `AMBIGUOUS` with its candidates

#### Scenario: the one case where "nothing to allocate" is not a missing slot

- **WHEN** the customer has zero open invoices
- **THEN** the allocation slot reads `NO_MATCH` (an advance is a legitimate
  answer) rather than `MISSING`

### Requirement: A transaction draft is the only input to building a proposal

The proposal step MUST take a ticket id plus the **current** values of the form,
and MUST re-read ERPNext (customer, live open invoices, live outstanding
amounts) before building anything. Prefill MUST NOT be reused as authority: a
value the user changed wins, and a value the user did not send is not invented.
Every form value MUST be re-validated server-side — the client's copy is a
request, never a fact.

#### Scenario: the form's values are re-validated server-side

- **WHEN** a request sends values that violate the locks (two methods, a missing
  allocation while invoices are open, a total that does not match, an amount
  above the live outstanding, or another customer's invoice id)
- **THEN** the answer is a refusal with the matching machine code and no
  proposal — the lock holds even if the client ignores it

#### Scenario: the answer is the ordinary proposal shape

- **WHEN** the form is valid
- **THEN** the answer carries the existing `erpn.proposal/v1` object with
  `submit_now:false` (nothing is executed), plus the server's own summary

#### Scenario: a client-supplied total can only fail a request

- **WHEN** the request carries a total that differs from the server's arithmetic
- **THEN** the request is refused with the client-authority code, and the number
  never changes what is proposed

### Requirement: The propose route never writes

The collect proposal step MUST be read-and-build only. It MUST NOT reference,
import, or reach any write tool, and `/execute` MUST remain the only door that
writes to ERPNext. A static check over the collect path MUST find no write
reference, and every refusal on this path MUST carry no proposal.

#### Scenario: nothing on the collect path can write

- **WHEN** the collect path's sources are scanned for a write-gateway reference
- **THEN** no match is found, and the route's only effects are reads plus the
  returned proposal

### Requirement: Open invoices are never selected automatically

The flow MUST NOT choose an invoice on the user's behalf — never by FIFO, never
oldest-first, never newest, never nearest, never by amount. With one or more
open invoices, an explicit allocation list is mandatory and each entry must be
positive and not exceed that invoice's live outstanding; with zero open
invoices, the allocation list MUST be empty and the receipt is an advance. A
reference to an invoice that is not open for this customer MUST be refused.

#### Scenario: open invoices require an explicit allocation

- **WHEN** the customer has open invoices and the request carries no allocation
- **THEN** the request is refused with the missing-field code and a message
  saying the system does not pick invoices for the user

#### Scenario: a settled customer cannot receive an allocation

- **WHEN** the customer has no open invoices and the request allocates to one
- **THEN** the request is refused, because the server cannot see that open
  invoice — the advance path is the empty allocation list

#### Scenario: no automatic selection exists in the primitives

- **WHEN** the transaction primitives are scanned for an invoice-selection
  helper (FIFO/oldest/first/newest)
- **THEN** none exists, and no sort of the open invoices is performed

### Requirement: One payment method per collection

A single collection MUST carry exactly one payment method: cash **or** bank
transfer. Two methods on one request MUST be refused with the method-count code
(a cash-plus-transfer collection is two collections, two documents). The same
method MUST NOT be declared twice, and the amount MUST be a positive integer
number of VND.

#### Scenario: cash plus transfer is refused

- **WHEN** a request carries two payment methods for one collection
- **THEN** the request is refused with the method-count code and no proposal

#### Scenario: one method is the only accepted shape

- **WHEN** a request carries exactly one method with a positive integer amount
- **THEN** the method passes validation and the summary is computed from it

### Requirement: A client-supplied total is a claim, not a payment channel

A summary MUST be computed by the server; the client's total is only ever an
input to compare against it. A credit remainder MUST be modelled as a number
(the difference between the document total and the amount received), never as a
payment method or an account. Line discounts and an order-level discount MUST
stay separate fields and MUST NOT be merged.

#### Scenario: the credit remainder is a number

- **WHEN** the paid amount is below the document total
- **THEN** the summary reports the remainder as a number, and no `credit`
  payment method exists in the primitives

### Requirement: payment.create is canonical and payment.collect is an alias of the same policy

`payment.create` MUST remain the canonical capability id for a collection, and
`payment.collect` MUST resolve to that same record — the same executor and the
same policy, not a copy. Answers MUST report the canonical id. An alias MUST
NOT be executable under its own name, MUST NOT collide with a real capability
id, MUST NOT point at another alias, and MUST point at an existing WRITE
capability that is not forbidden on the AI path; each of these MUST fail
validation of the contract.

#### Scenario: both ids describe one capability

- **WHEN** the contract is asked for `payment.create` and for `payment.collect`
- **THEN** both resolve to the same capability record, and the alias list reports
  the canonical target

#### Scenario: a client using the alias gets one flow

- **WHEN** a client addresses the collection by its alias
- **THEN** the handoff and the proposal name the canonical id, so the alias
  cannot open a second flow

#### Scenario: a broken alias fails the contract

- **WHEN** an alias is defined whose key shadows a real capability, whose target
  does not exist, whose target is another alias or a READ capability, or whose
  target is forbidden on the AI path
- **THEN** contract validation fails instead of starting the server

#### Scenario: an alias is never executable directly

- **WHEN** execution is attempted for an alias id
- **THEN** it is refused as forbidden on the AI path — only the canonical id may
  be executed
